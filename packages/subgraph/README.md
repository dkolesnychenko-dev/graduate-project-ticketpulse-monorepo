# 🎟️ @ticketpulse/subgraph

> **High-performance indexing layer for the TicketPulse NFT ticketing ecosystem.**
> 
> Responsible for indexing events from the `TicketPulseFactory` and dynamically tracking every `TicketPulseEvent` clone deployed by the factory. It provides a highly optimized GraphQL API for the frontend to query ticket ownership, primary market sales, secondary market FIFO queues, user balances, and complete activity history.

## 🏗️ Architecture & Implementation

We use the **native Graph CLI capabilities** for multi-environment deployments.

- **`subgraph.template.yaml`**: The source of truth for the subgraph manifest. It uses `{{mustache}}` placeholders for network-specific values (addresses, start blocks).
- **`subgraph.yaml`**: The generated manifest used by the Graph CLI. **Do not edit this file directly** as it is overwritten during the build process and is ignored by Git.
- **`networks.json`**: Central configuration for production addresses (Sepolia, Mainnet).
- **`networks.local.json`**: Local configuration automatically synced from Foundry deployments.
- **`schema.graphql`**: Defines the robust, analytics-ready entity structure.
- **`src/mapping.ts`**: Highly optimized AssemblyScript mapping logic.

### Key Implementation Details

1. **Dynamic Data Sources (Templates)**: 
   The `TicketPulseFactory` contract emits an `EventCreated` event whenever a new event is launched. Our subgraph manifest includes a **Template** for the `TicketPulseEvent` contract.
   The `handleEventCreated` function in `mapping.ts` calls `TicketPulseEvent.create(address)`, which tells the Graph Node to start tracking the new contract dynamically.

2. **Idempotency & `getOrCreate` Pattern**: 
   Every entity that might exist (like a `User` or a `Balance`) is loaded via a `getOrCreate` helper. If the entity doesn't exist, it is initialized with safe default values (e.g., `BigInt.zero()`) to prevent crashes during reorgs.

3. **FIFO Queue Indexing**: 
   The secondary market operates on a First-In-First-Out basis. The subgraph carefully tracks `BuyOrder` and `SellOrder` entities, including their queue status (`ACTIVE`, `COMPLETED`, `CANCELLED`).

4. **Comprehensive Audit Trail (`ActivityLog`)**: 
   Every significant action on the blockchain is recorded as an `ActivityLog` entity. This provides the frontend with a complete "Activity Feed" view.

5. **Metadata Strategy & API Performance**: 
   While IPFS is the primary source of truth for rich event metadata, critical fields (`title`, `description`, `ticketType`, `startTime`) are mirrored directly in the Subgraph entities from on-chain constructor arguments. This allows filtering directly at the API level avoiding the "N+1 problem".

This package is part of a monorepo. To set it up:

1. **Install Dependencies**: `pnpm install` (from the root or here).
2. **Build & Codegen**: `pnpm build` (this will automatically run `graph codegen` to generate types from your schema and ABIs).

## ⚙️ Code Generation & Deployment Flow

To understand how the subgraph compiles and runs, here is the exact sequence of events:

1. **Schema and ABIs**: Define your data entities in `schema.graphql` and provide paths to your ABIs in `subgraph.yaml`.
2. **Type Generation (`pnpm codegen`)**: Reads the schema and ABIs to generate AssemblyScript types inside `generated/`. Creates strict classes for schema entities and contract events. **Mappings will not compile without this step**.
3. **Dynamic Templates (`templates.ts`)**: Because `TicketPulseFactory` spawns new contracts, `codegen` generates `TicketPulseEvent` inside `generated/templates.ts`.

> [!TIP]
> **When to run what?**
> - **Changing ABIs or `schema.graphql`?** $\rightarrow$ Mandatory `pnpm codegen`.
> - **Changing logic in `mapping.ts`?** $\rightarrow$ `pnpm deploy:local`. (Includes `codegen` out of the box).

## 💻 Local Development Workflow

When developing locally, we use a local Graph Node running via Docker, connected to a local Anvil blockchain.

### 1. Start Infrastructure & Blockchain
Refer to the **[Zero-to-Hero Setup Guide](../../README.md#-zero-to-hero-setup-guide)** to launch the Docker infrastructure (`pnpm infra:up`) and Anvil.

### 2. Deploy Contracts to Local Anvil
Follow the instructions in the [contracts README](../contracts/README.md#-local-development-workflow) to deploy to your local blockchain.

### 3. Deploy the Subgraph
Compile and deploy the subgraph. The configuration is fully automated:

```bash
# 1. Create the subgraph on your local node (Run only once per environment reset)
pnpm create:local

# 2. Deploy the subgraph (Run every time you change mappings or schema)
# This command:
#   - Syncs the latest Factory address from Foundry
#   - Generates subgraph.yaml from the template
#   - Runs codegen and deploys
pnpm deploy:local
```

Your local GraphQL endpoint will be available at:  
`http://localhost:8000/subgraphs/name/ticketpulse/subgraph`

### 🕵️ Deep Database Inspection (DBeaver)

While the GraphQL API is primary, you can inspect raw PostgreSQL data:
- **Connection**: `localhost:5432`, DB: `graph-node`, User: `graph-node`, Pass: `let-me-in`.
- **Location**: Graph Node creates dynamic schemas for each deployment. Check the `public.deployment_schemas` table, find your IPFS CID, and open the corresponding schema (e.g., `sgd4`).

## 🚀 Production Workflow (Subgraph Studio)

For Testnet (`base-sepolia`) and Mainnet (`base`), we publish to
**The Graph Studio** — Edge & Node's hosted indexer that issues a
queryable GraphQL endpoint backed by the decentralised Graph Network.

### 1. Prepare Subgraph Studio

1. Visit <https://thegraph.com/studio/> and connect your wallet.
2. Click **Create a Subgraph** — name it something explicit like
   `ticketpulse-sepolia` or `ticketpulse-mainnet`. Each chain typically
   gets its own subgraph in Studio (the slug becomes part of the
   query URL).
3. From the new subgraph's dashboard, copy:
   - **Deploy Key** — used by `graph deploy` to authenticate (private,
     never commit).
   - **Query URL** — the public GraphQL endpoint your frontend will
     point at. Looks like
     `https://api.studio.thegraph.com/query/<id>/ticketpulse-sepolia/version/latest`.
4. Take note of the **Subgraph slug** (e.g. `ticketpulse-sepolia`).
   It's the second argument to `graph deploy` and is set in the
   `deploy:studio:*` scripts.

### 2. Deploy the Smart Contracts

Run [`pnpm --filter @ticketpulse/contracts deploy:base-sepolia`](../contracts/README.md#-production--testnet-deployment)
(or `:base`) — it prints the Factory address and writes broadcast
metadata to `packages/contracts/broadcast/Deploy.s.sol/<chainId>/run-latest.json`.
You'll need that address in step 4.

### 3. Authenticate the CLI

```bash
pnpm auth:studio
# Paste the Deploy Key from step 1.3 when prompted.
```

The Deploy Key is stored in `~/.npm/_npmrc` for the `@graphprotocol`
scope — it never leaves your machine.

### 4. Update Production Configuration

Update `networks.json` **once per chain** with the Factory address you
just deployed:

```json
"base-sepolia": {
  "TicketPulseFactory": {
    "address": "0xYOUR_LIVE_FACTORY_ADDRESS",
    "startBlock": 12345678
  }
}
```

`startBlock` is the block number containing the Factory's `EventCreated`
emission — usually the deployment transaction's block. Setting it
correctly means Graph Node skips re-scanning the entire chain history.

> [!TIP]
> Grab the block number from the Basescan transaction page or from
> `run-latest.json` (`receipts[0].blockNumber`).

### 5. Deploy to Studio

The build system handles all manifest templating + ABI codegen for you:

**For Base Sepolia:**
```bash
pnpm deploy:studio:sepolia
```

**For Base Mainnet:**
```bash
pnpm deploy:studio:mainnet
```

These commands run `sync-networks.js <network>` automatically to
generate `subgraph.yaml` from `subgraph.template.yaml` with the right
network + address before calling `graph deploy`.

After a successful deploy you'll see a "Version" hash and a sync
progress meter in Studio. Wait for the indexer to reach the latest
block before pointing the frontend at it.

### 6. Wire the Frontend

Copy the Query URL from step 1.3 into `apps/web/.env.local`:

```dotenv
NEXT_PUBLIC_SUBGRAPH_URL=https://api.studio.thegraph.com/query/<id>/ticketpulse-sepolia/version/latest
```

Optional: gate the endpoint with a [Studio API Key](https://thegraph.com/docs/en/subgraphs/quick-start/#authorize-your-deployment)
for higher rate limits, then set `GRAPH_API_KEY` server-side — it's
attached as `Authorization: Bearer <key>` by `apps/web/api/graphql/route.ts`
and never reaches the client bundle.

## 📖 GraphQL API & Frontend Documentation

The Subgraph exposes an optimized GraphQL API. The Graph automatically generates `where` and `orderBy` filtering capabilities.

- **API Endpoint:** `http://localhost:8000/subgraphs/name/ticketpulse/subgraph`
- **GraphiQL Playground:** `http://localhost:8000/subgraphs/name/ticketpulse/subgraph/graphql`

### Generating API Documentation (Magidoc)
We use [Magidoc](https://magidoc.js.org/) to automatically generate a beautiful static site containing our full GraphQL API documentation.

```bash

pnpm docs:generate

# Preview the generated documentation locally
pnpm docs:preview
```

## 🔒 Security & Best Practices

- **Strict Typing:** AssemblyScript types are strictly enforced to prevent runtime errors during indexing.
- **Audit Logs:** Every entity update includes `updatedAt` and `updatedTxHash` fields for debugging and transparency.
